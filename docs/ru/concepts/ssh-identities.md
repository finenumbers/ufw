# SSH-идентификации

**SSH-идентификация** хранит переиспользуемые учётные данные подключения: username, метод аутентификации и зашифрованные секреты. Каждый **сервер** ссылается на одну идентификацию.

## Методы аутентификации

| Метод | Хранимый секрет | Типичное использование |
|-------|-----------------|------------------------|
| **Пароль** | SSH-пароль | Простой lab или legacy hosts |
| **Приватный ключ** | PEM private key | Production keys без passphrase |
| **Приватный ключ + парольная фраза** | Ключ и passphrase | Зашифрованные private keys |

Секреты шифруются при хранении **AES-256-GCM** с `APP_ENCRYPTION_KEY`. Расшифровываются только в памяти при открытии SSH-подключения.

## Создание и редактирование

1. Боковая панель → **SSH-идентификации**
2. **Добавить идентификацию** или откройте строку → **Изменить**
3. Обязательные поля: display name, SSH username, auth method, secret(s)

При **редактировании** пустые поля password/key оставляют текущий секрет без изменений.

Validation отклоняет пустые имена и недопустимые auth combinations до сохранения.

## Привязка к серверам

При создании или изменении сервера выберите идентификацию из dropdown. Смена identity сервера запускает SSH verification при save, если изменились параметры подключения.

## Удаление идентификации

Удаление блокируется, пока на identity ссылается хотя бы один сервер. UI показывает связанные серверы. Сначала переназначьте или удалите эти серверы.

## Заметки по безопасности

- Секреты identity попадают в **экспорт конфигурации** (JSON v2) после подтверждения пароля — относитесь к export как к highly sensitive
- Ротация `APP_ENCRYPTION_KEY` без повторного ввода секретов делает существующий ciphertext нечитаемым — планируйте rotation осторожно
- Одна identity может использоваться многими серверами (один admin user, один key)
